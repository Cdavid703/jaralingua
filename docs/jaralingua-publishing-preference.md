# Standing publication authorization

The project owner explicitly authorized commit, push and deployment of the Food Quantities iPad correction, and instructed that future requested changes should follow this workflow without asking for separate approval every time.

For work the owner requests in this project:

1. Implement and test the requested change.
2. Review and commit only its precise files, then push normally (never force-push).
3. Review the publisher preview, deploy the explicit files, and verify production.
4. Report the result and any remaining limitation.

This is authorization for the normal publication workflow, not for unrelated pending work, destructive changes, new credentials/privileges, student-record mutations, or expanding the requested scope. Preserve concurrent user work. Stop for a genuinely new risk or missing decision rather than assuming broader authority. Backend changes still require appropriate separate testing and deployment safeguards; a static publisher must not restart services or change databases.

Existing development work (including Stone Soup and pronunciation) is not implicitly included in the current Food Quantities release. Existing technical protections, backups, explicit-path publication, and verification remain required.

This explicit standing instruction supersedes older project guidance asking for fresh publication approval for each routine requested change. It may be revoked or narrowed by the owner at any time.
